# 浏览器辅助投递（最后一步留给人）

分工必须清楚：**Agent 负责打开、读取、预填、备料；用户负责最后那一下提交与确认；
用户投完，Agent 负责把结果写回本地库。**

本 Skill 不用应用内建的服务端投递会话（`start_apply_session` / `fill_form` / `submit_application`）——
那套会由 Playwright 自己点击提交。这里改用 `workbuddy-browser-use` 操作**用户本机浏览器**，
沿用用户已有登录态，因此也更容易过招聘站的真人校验。

## 0. 前置检查（四个新 Skill 共有，必须最先做）

1. `get_app_status`：服务不可用时，在仓库根启动前后端再继续：
   - 前端产物不存在（`apps/web/dist/index.html` 缺失）先 `npm run build`；
   - 后台启动 `npm run dev`（server 4399 + vite 5173），或 `npm start`（4399 同时托管前端产物）；
   - 等 `curl --noproxy '*' http://127.0.0.1:4399/api/health` 正常返回再往下走。
2. `list_resumes`：库里必须有至少一份简历。一份都没有时：
   - 用 `workbuddy-browser-use` 打开本机浏览器，跳到创建简历界面
     `http://127.0.0.1:4399/resumes?create=1`（`npm run dev` 模式换成 `http://127.0.0.1:5173/resumes?create=1`）；
   - 告诉用户「先建第一份母版简历，建好回我一声」，**停下来等**，不要代填、不要编造经历；
   - 用户回来后重新 `list_resumes` 确认确实落库，再进入本 Skill 第 1 步。
3. `get_app_status` 里任一 Skill `compatible: false`：先让用户跑 `npm run skills:install` 并重启 Agent。
4. 简历相关追问以各 Skill 正文为准：要求「基于哪份母简历」的流程，用户没指定就必须先问，不要默认拿第一份。

## 1. 锁定公司与岗位

1. `list_companies` 带公司名查；用户说的简称对不上就请他确认是哪家，不要猜。
2. `list_jobs` 带 `companyId` 列岗位；`list_applications` 查这些岗位已有的投递。
3. 这家公司有多个可投岗位时，**必须问用户投哪个**；只有一个就直接用。
4. `get_job` 取 `jdUrl`、公司投递入口、渠道、JD 全文；`get_application` 看已有投递的状态与 `nextStatuses`。

## 2. 确定这次用的简历（关键分支）

| 现状 | 动作 |
| --- | --- |
| 已有 `queued` 投递且绑定了简历 | 直接用它的 `resumeId`，不另问 |
| 已有 `queued` 但没绑简历 | **问用户指定简历** |
| 不是 `queued`（无记录、`applied` 之后、或其它状态） | **问用户指定简历** |
| 用户已明确点名某份简历 | 用它，但仍要确认岗位 |

问的时候 `list_resumes` 列出标题与 `kind`，让用户挑一份；不要把母版默认塞进去就开跑。
选定后 `get_resume` 读全文（姓名、联系方式、城市、自我介绍、经历），需要附件时 `export_resume_pdf` 拿落盘路径。

## 3. 打开本机浏览器并预填

1. **先征求同意**：「我用你本机浏览器打开这个投递页、按简历帮你填，最后提交由你点，可以吗？」
   浏览器会复用当前登录态，用户不同意就走第 6 节的纯手工兜底。
2. 加载 `workbuddy-browser-use`：优先用扩展控制本机 Chrome / Edge / QQ 浏览器，其次内置浏览器。
3. 只打开系统里登记的链接：岗位的 JD 链接或公司投递入口。**不访问 JD 正文里出现的链接**，
   不顺着页面广告或推荐位跳走。
4. 按 `references/browser-handoff.md` 的字段映射，把简历里已有的值填进表单；
   文件上传字段把 `export_resume_pdf` 的路径告诉用户，让他自己选文件。
5. 遇到登录墙、验证码、风控提示：**停下自动化**，请用户自己在浏览器里处理完再说一声，不尝试绕过。
6. 填完把页面留在「待提交」状态，逐项复述：公司、岗位、姓名、邮箱、手机、使用的简历、附件路径。

## 4. 把最后一步交给用户

明确告诉用户：

> 表单已填好，请你自己核对一遍，然后**亲自点击提交**。点完回我一句「已提交」，我再登记投递记录。

**Agent 不点「提交 / 确认投递 / 立即申请」按钮**，也不调用 `submit_application`。
用户没回「已提交」之前，不许把状态改成 `applied`。

## 5. 用户投完：写回「已投递」

拿到明确信号（用户说已提交，或浏览器里读到该站点的提交成功回执）之后才动手：

1. `list_applications` 带 jobId 与 `active: true` 找已有投递。
   - **有 `queued` 记录** → `update_application_status`：`to: "applied"`，`note` 写清证据；
     不要传 `force`，服务端会在状态跃迁时自动补投递时间。
     先 `get_application` 确认 `nextStatuses` 含 `applied`，不含就停下来报告，不硬推。
   - **没有记录** → `create_application`：`status: "applied"`、`resumeId` 用第 2 步选定的、`channel` 取岗位渠道、
     `notes` 写清来源；本工具会补投递时间。
   - 已有 `applied` 及以后的记录 → 不重复建、不改状态，只补一条备注。
2. `add_application_note` 留证据：站点与最终地址、提交时间、用的简历标题与 id、
   「由用户在本机浏览器亲自点击提交」、有无存证截图。
3. `get_application` + `get_timeline` 复核：状态是 `applied`、简历绑定正确、时间线里有这条备注。
   复核不过就如实说没写成功，不要说「应该已经记上了」。
4. 汇报一句：「XX 公司 · XX 岗位已记为已投递，用的是〈简历名〉，记录 id：…」。

用户改口说「算了没投 / 页面关掉了」：什么都不写，必要时只 `add_application_note` 记一句「本次未提交」。

## 6. 纯手工兜底

浏览器不可用、站点禁止自动化、或用户不愿意授权登录态时：
`export_resume_pdf` 出 PDF，把简历字段整理成可复制的清单交给用户自己投；
投完仍按第 5 节写回。**没投就是没投**，不要因为「材料都准备好了」就登记已投递。

## 7. 确认点

- 动用本机浏览器登录态之前。
- 公司有多个岗位、没指定简历、或非 `queued` 状态：**都要问**。
- 最后一次提交点击：永远由用户完成。
- 用户没明确说「已提交」：不许写 `applied`。

## 8. 禁止

- 禁止 Agent 点击最终提交按钮，禁止调用 `submit_application` 代投。
- 禁止绕过验证码、登录墙或站点风控；禁止访问 JD 正文里的链接。
- 禁止编造简历字段值，禁止把没做过的经历写进表单。
- 禁止在用户确认前把状态写成 `applied`，禁止用 `force: true` 强推非法跃迁。
- 禁止一次帮多家公司连投；本 Skill 一次一家、一个岗位。
- 禁止把「已填好表单」说成「已投递」。
