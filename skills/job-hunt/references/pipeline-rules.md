# 流水线规则（job-hunt 参考）

## 状态机

11 个状态，跃迁由服务端强制校验，非法跃迁返回 `INVALID_TRANSITION` 并带 `allowed` 列表。

```
lead → queued → applied → screening → assessment → interview → offer → accepted
                    ↘ rejected / ghosted / withdrawn（终态）
```

要点：

- **`lead → applied` 不允许**：先入队（`queued`）再投。否则「计划投但没投」无处安放。
- 任意活跃状态都可以 → `withdrawn`（用户随时能撤回）。
- 终态不能直接复活，必须 `force: true` + `reason`，会写进事件流留痕。
- 状态为 `applied` 及以后必须有 `appliedAt`，否则后续跟进规则算不出天数。

## 跟进规则（纯函数现算，不落库）

| 规则 | 触发条件 | 建议动作 |
| --- | --- | --- |
| 无回音催办 | `applied` 且距今 > 7 天 | 问用户是否催；催了就记备注 |
| 面试后感谢信 | 有面试且距今 > 3 天、无 feedback | 提醒发感谢信并记备注 |
| offer 倒计时 | `offer.deadline` 距今 ≤ 2 天且 `pending` | 最高优先级，先谈决定 |
| 静默流失 | `applied`/`screening` 且距今 > 30 天 | 建议标 `ghosted`（需确认） |

规则是**现算**的：处置后条件不再成立，任务自然消失。所以没有「删除任务」这个动作——
用户说「这个我不管了」，正确做法是推进状态或推后 `nextActionAt`，而不是假装它不存在。

## 北极星口径

```
本周有效投递 = 本周 appliedAt 的投递中，fitScore ≥ 60 且 resumeId 非空的条数
```

- 目标默认 8 份/周（单周认真投的下限）。
- 「投了 20 份但没有一份定制简历」在本口径下等于 0——这是刻意的。

## 漏斗口径

按「到达过的最高阶段」去重统计，不是「当前状态」。

进过面试后挂了的人，仍然计入「筛选通过」。否则「面试数 > 筛选数」的怪象会让
转化率永远偏低，用户会去优化错误的一环。

## 常见误判

- **「面试很多但没 offer」** 不一定是面试能力问题，先看漏斗：如果 `screening → interview`
  转化很低，问题在简历与岗位匹配；如果 `interview → offer` 才低，才是表达与临场。
- **「投得少」** 往往不是懒，是 `fit ≥ 60` 的岗位不够。此时该做的是补岗位，不是催投递。
